# Architecture Decision Records — Estudio MVP

---

## ADR-001: 4 Independent Services vs. Modular Monolith

**Status:** Accepted

**Context:**
The MVP has 4 functional modules (image analysis, history/trends, accounts, trust/data) that could be deployed as a single modular monolith or as separate services. The team is a solo developer with ~5h/week capacity, and the deployment target is a local Kubernetes cluster. The academic course curriculum covers Kubernetes multi-service deployments.

**Decision:**
4 independent services — one per functional module — each as a separate Kubernetes Deployment.

**Consequences:**
- Each service can be developed, deployed, and restarted independently.
- The K8s multi-service topology is required by the course curriculum (modules 4-8 cover exactly this).
- Adds operational complexity (4 Deployments, 4 Services, Ingress routing) for a solo developer — mitigated by the course structure, which teaches this progressively.
- Inter-service communication adds latency and requires contracts (partially addressed by the shared database approach in ADR-004).

**Alternatives Considered:**
- Modular monolith (1 Node.js server, 4 modules): simpler to develop, but misaligned with the academic curriculum and the course's K8s focus. Rejected.
- 2-service topology (Core API + Frontend): reduces K8s complexity but removes the bounded context isolation the domain design is built on. Rejected.

## ADR-002: IngestionService as Exclusive Blob Owner

**Status:** Accepted

**Context:**
User images are the most sensitive data in the system. The privacy requirement (FR-4.2) states that no user can access another user's images. The question is which component controls blob storage read/write access.

**Decision:**
IngestionService is the exclusive owner of blob storage. All other services and the frontend access image data only through IngestionService-issued signed URLs or text/score data — never by accessing the blob store directly.

**Consequences:**
- A single enforcement point for the image privacy boundary.
- The frontend displays thumbnails via signed URLs generated by IngestionService, not by direct blob URLs. This adds a round-trip but is necessary for privacy.
- TrustService's deletion cascade must call IngestionService to delete blobs — it cannot reach blob storage directly. This creates a service dependency for the deletion flow.

**Alternatives Considered:**
- Shared blob store accessed by multiple services: simpler implementation but eliminates the single enforcement point. Rejected.
- Dedicated media service: adds complexity without benefit at MVP scale. Rejected.

## ADR-003: Relational Storage for Score Time Series; Trend Calculated at Query Time

**Status:** Accepted

**Context:**
The trend calculation requires a time series of per-category scores per user. The design choices are: (a) store raw scores and calculate on read, (b) store raw scores and pre-compute trend on write, or (c) use a document store.

**Decision:**
Relational table `category_critiques (upload_id, category_id, score, feedback_text, confidence)` in the ingestion schema. The trend is calculated at read time by ProgressService: a linear regression over the score column, filtered by user and category, ordered by upload timestamp.

**Consequences:**
- Simple schema; no pre-computation artifacts to keep in sync.
- Query performance may degrade as history grows (>100 uploads per user per category). At MVP scale (free tier: 10 uploads/month, small user base), this is not a concern.
- The linear regression runs in application code (Node.js), not in the database. This keeps the DB simple but means the calculation scales with application instances, not with DB compute.

**Alternatives Considered:**
- Pre-computed trend column (updated on each upload): adds write complexity and a double-write problem. Rejected for MVP.
- TimescaleDB or a time-series DB: over-engineered for the MVP scale. Rejected.
- Document store (MongoDB): increases operational complexity (a second database type) without meaningful benefit for this data shape. Rejected.

## ADR-004: Single PostgreSQL Instance, Four Isolated Schemas

**Status:** Accepted (MVP pragmatism — not recommended for production)

**Context:**
Strict bounded context isolation recommends one database per context. For a local K8s MVP with a solo developer and ~5h/week capacity, running 4 PostgreSQL instances is excessive.

**Decision:**
One PostgreSQL instance, four schemas: `ingestion`, `progress`, `identity`, `trust`. Each service's application code accesses only its own schema via separate connection credentials. Exception: ProgressService reads from the `ingestion` schema (read-only) for trend calculation.

**Consequences:**
- One database to manage, back up, and configure in K8s.
- Schema-level isolation is weaker than instance-level isolation but sufficient for a single-developer MVP.
- The ProgressService cross-schema read is the intentional exception. It is read-only and uses a dedicated read-only DB user for the ingestion schema.
- If the team scales, migrating each schema to its own instance is straightforward (no cross-schema foreign keys in the schema definitions).

**Alternatives Considered:**
- 4 separate PostgreSQL instances: operationally correct but excessive for the MVP. Rejected.
- A single schema with all tables: eliminates access boundaries entirely. Rejected.
